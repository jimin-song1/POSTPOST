## 1. 요약

V34에서 추가한 목표와 산출물 필드를 실제 중복 판정과 후보 선정에 연결했다. 핵심은 문장이 아니라 **장면 규칙표에 고정한 목표 키와 산출물 키**로 비교한다는 점이다.

- RC11 09번: 추상 후보(legacy, 생성 보류)에서 구조화 후보 `V56-B2-P01-09-dayBranch-hourStem`(READY_FOR_REVIEW)으로 바뀌었다. 앞 장과 겹치지 않는 새 원국 위치쌍(일지 戌, 시간 辛)을 쓴다.
- RC11 10번: 미선정에서 09번과 연결된 부담 후보 `V56-B2-P01-10-monthBranch-hourStem`(READY_FOR_REVIEW)으로 바뀌었다.
- 12개 명식: 119/120 → 120/120 선정, 구조화와 원고 검토 가능 96 → 98.
- 01~08번 선정은 12개 명식 모두 V34와 동일하다(자동 검사로 고정).
- 09번이 앞 장의 원국 위치쌍을 그대로 재사용한 경우: V34 12/12 → V35 2/12.
- 09번 선정 결과 중 앞 장과 목표나 산출물이 같은 경우: 0건(자동 검사로 고정).

이 수치는 선정 규칙의 계약을 검증한 결과다. 실제 고객의 성격 적중률이나 AI 원고 품질을 뜻하지 않는다.

### 2.2 `personality-claim-guard.v1.ts`

`goalOutputRelation()`을 추가하고 `behavioralOverlap()`의 판정 순서를 다음처럼 바꿨다.

1. 행동 문장이 같으면 중복 (V29 하한, 무조건)
2. 규칙표 목표 키나 산출물 키가 같으면 중복 (문구와 모티프가 달라도)
3. 양쪽 모두 규칙표 근거가 있고 목표와 산출물이 **둘 다** 다르면, 모티프 겹침만으로는 중복으로 보지 않음. 단 호출자가 `allowGoalOutputDistinct`를 켠 경우에만
4. 그 밖(근거 없음, 문구 추출만 있음)은 V34 모티프 규칙 그대로

근거가 없거나 문구 추출뿐이면 `UNVERIFIED`가 되며, 이 상태는 같음을 확인하는 데에만 쓰이고 독립성을 입증하지 못한다. 계약 검증(`verifyGeneratedBehaviorContract`)에 목표와 산출물 필드 6개를 추가해 생성 후 편집을 막았다.

### 5.3 선정된 09번

- 상황: 새로운 절차의 이유를 이해한 뒤 실제 적용 여부를 판단할 때
- 행동: 시급한 요청의 우선 책임을 정리한 다음 익숙한 설명의 근거를 확인하는 두 과정을 연결해 새 절차를 어디까지 적용할지 정하려는 모습
- 목표: 새 절차를 실제 일에 어디까지 적용할지 정하는 것
- 산출물: 공식 기준과 대조해 정한 적용 범위
- 판단기준: 압박 속 우선 처리할 책임 / 이미 알고 있는 정보와 이해의 근거 (일지 편관, 시간 정인)
- 반대 조건: 이미 충분히 익숙한 절차라면 별도의 설명을 확인할 일이 줄어들 수 있음

| 비교 | 앞 장 목표 / 산출물 | 09번 목표 / 산출물 | 공통 모티프 |
| --- | --- | --- | --- |
| 01번 | 새 일을 어디서부터 시작할지 / 정해진 시작 단계 | 적용 범위를 정함 / 적용 범위 | verification, rules |
| 05번 | 선택 전 우선 조건을 정함 / 우선 확인할 조건 | 위와 같음 | role-boundary, verification, rules |

공통 어휘가 있으므로 원고 작성 시 01, 05, 08번과 같은 표현을 반복하지 않는지 사람이 확인해야 한다.

### 5.4 연결된 10번

- 상황: 정해진 절차를 모두 지키려다 일정과 조율해야 할 때
- 부담 가설: 압박 속 우선 처리할 책임을 모든 상황에 적용하려 하면 이미 알고 있는 정보와 이해의 근거를 고려할 여유가 줄어들 수 있음
- 근거: 월지 戌(편관), 시간 辛(정인). 09번과 시간 辛 한 곳을 공유

## 8. 미해결 문제

1. **09번 문장 틀은 여전히 조립식이다.** V35.1에서 근거 없는 순서와 겁재 모순은 고쳤지만, 십성별 구절 두 개를 붙이는 구조는 남아 있다. 계열별 장면 문장(`STRENGTH_SCENES.action`)을 쓰는 방식은 V30에서 근거 연결이 나빠진 이력이 있어 이번에는 하지 않았다.
2. **목표와 산출물 규칙표는 편집 판단이다.** 계열 쌍마다 목표를 하나로 정했으므로, 같은 계열의 다른 십성 조합(예: 편관, 정인과 정관, 편인)도 같은 목표를 갖는다. 명리 전문가의 표 검토가 필요하다.
3. **02, 03, 10번에 목표와 산출물이 없다.** 이 장들과 겹치는 09번 후보는 여전히 모티프 규칙으로만 판정된다. RC04, RC12의 일부 09번 후보가 02, 03번 때문에 탈락하는 이유다.
4. **10번 의미 중복 경고가 2건 늘었다** (RC01 02~10, RC11 08~10). 10번은 아직 목표와 산출물 비교를 하지 않는다.
5. **RC11 09번은 01, 05, 08번과 어휘를 공유한다.** 목표와 산출물은 다르지만 원고에서 같은 표현이 반복되지 않도록 사람이 검토해야 한다.
6. 12개 명식 결과는 Swiss 절기 fixture 기준이며 운영 JPL 계산 경로와 같지 않다.
7. RC11의 03, 04, 07번은 아직 추상 후보(생성 보류)다. V35 범위 밖이다.
8. 09번 상황 문장의 어휘가 01번과 겹치는 경우가 있다(RC11 "이해한 뒤"). 참고 예문에서는 산출물로 시작해 구별했지만, 원고 단계 검토가 필요하다.

## 9. 고객용 원고 검증 여부

실제 AI API를 호출하지 않았다. 7장 예문은 모두 내부 행동 가설이다. `V35_예시문장.md` 3장의 RC11 고객 문체 예문은 Claude가 가설만 보고 직접 쓴 참고용이며, 파이프라인 출력이나 검증된 원고가 아니다.

## 10. 배포 가능 여부

**배포 불가 (`releaseReady=false`).**

- 프로젝트 지정 환경에서 `npm test`, `npm run typecheck`, `npm run build`를 실행하지 못했다(이 환경에서 npm 레지스트리 차단).
- 실제 AI 원고 검증과 사람의 원고 검토가 없다.
- 미해결 문제 1, 2번은 고객 노출 전에 처리가 필요하다.

다음 단계로 권장하는 순서:

1. 의존성을 설치할 수 있는 환경에서 `npm ci && npm test && npm run typecheck && npm run build`
2. 명리 검토자가 `STRENGTH_GOALS`, `SECTION_GOALS` 표 확인
3. RC11과 바뀐 09번 9건으로 실제 AI 원고를 생성해 중복 표현 검토
4. 09번 문장 틀 개선(V36 후보)과 10번 목표와 산출물 비교 도입
