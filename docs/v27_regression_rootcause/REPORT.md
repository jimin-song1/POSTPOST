# 사주빛 V27 — 회귀 검사 실패 원인 분석

V26 소스를 기반으로 실패했던 네 검사 스위트를 재실행하고, 생성된 JSON의 개별 실패 항목을 확인했다. **이번 버전은 검증·진단 개선이며 실제 성격 후보 선정 로직은 수정하지 않았다.**

| 검사 | 통과 | 실패 | 확인된 원인 |
| --- | --- | --- | --- |
| V6 | 9/10 | 1 | 04의 `scenarioRuleId`가 옛 `P01-04:output|` 접두어로 시작할 것을 요구 |
| V8 | 15/16 | 1 | V6과 같은 04 옛 규칙 ID 접두어 검사 |
| V13 | 10/15 | 5 | 118→115 선정, 69→63 구조화, B05/B10의 09·10 선정 여부 변화, 09 규칙 ID suffix 변화 |
| V15 | 6/7 | 1 | 09 행동 설명 종류가 정확히 3개여야 한다는 과거 기대와 현재 5개가 충돌 |

따라서 **실패 스위트 4개, 실패한 테스트 단언은 8개**다. V6·V8·V15는 역사적인 형식·고정 수치 단언이 원인이지만 그 결과만으로 현재 계약이 옳다고 증명된 것은 아니다. V13의 일부 실패는 실제 선정 선택이 바뀐 것으로 더 엄격한 조사 대상이다.

## 다음 수정 기준

1. V6/V8: 04 규칙 ID 형식과 실제 십성 근거 연결이 일치하는지 확인 후 새 현재 버전 계약 테스트를 작성한다. 과거 검사는 역사적 회귀 기록으로 유지한다.
2. V15: 현재의 5종이 서로 다른 의미인지, 동일 명식에서 결정론적으로 반복되는지 시험하고 과거 3종 고정 검사는 역사적 기준으로 분리한다.
3. V13: B05와 B10의 후보 생성·탈락·선정 단계별 내역을 현재와 V13 원본 코드로 비교하여 의도된 안전 차단인지 회귀인지 확정한다. 수치만 바꿔 통과시키지 않는다.
4. 실제 09·10 복구와 미승인 항목 정리, 전체 타입 검사와 AI API 원고 시험 전까지 배포 차단을 유지한다.

검증 범위: 해당 Node 오프라인 테스트. 전체 앱 빌드·타입 검사·실제 API 고객용 원고는 검증되지 않았다.
